# 浏览服务开发与正式运行

- 本目录的网页和后端日常修改默认在原工作区的 `main` 目录进行。开始修改前核对当前目录、分支及未提交改动；不因会话曾关联开发worktree而自动进入支线。
- 只有用户明确要求使用分支，或说明具体需要并与用户约定后，才使用独立分支／worktree；不默认创建或恢复开发目录，也不默认启动8783。原 `codex/browser-dev` 已同步主线并停用，开发工作目录归档。
- `main` 目录用于正式服务，端口8782。代码修改、本地提交与发布分开；构建正式前端及重启服务按本次用户授权范围执行，不能把普通代码修改自动扩大成发布。启动／停止使用目标目录的脚本，核对端口、代码目录和资料目录；不覆盖无关未提交改动。
- 上条发布边界针对Git操作：仅要求提交、合并、同步分支或整理代码，不因此取得发布授权。用户在8782提出网页功能、样式或修复要求时，Agent的交付范围默认包含验证、Git提交、正式构建、重启8782及页面核对，不在提交后另等一次发布确认；开始发布前说明短暂重启即可。用户明确只讨论、暂不发布、只改代码／规则，或双方约定开发环境、发布时间时，按该范围执行。这两种情况分别判断，不把Git的发布边界套成网页任务的额外审批步骤。
- 项目创作与制作资料仍在原工作区按既有规则维护。另行约定开发环境时，可通过其 `runtime/service.json` 指向原工作区，共用真实资料；该本机配置不入Git。开发页的意见保存／清空会直接写入正式项目资料；自动化写入测试使用临时目录或临时API响应，不把测试内容写入真实资料。
- 每次完整任务只提交本次获授权的改动，不混入其他会话的修改。使用支线时，合并与发布按当次约定执行。
- 服务版本以 `frontend/package.json` 为唯一来源；每次将新代码用于正式服务都须递增版本并更新版本记录，普通提交、项目资料更新及同版本重启不递增。发布先检查并构建，再通过统一启动器重启正式服务，核对 `/api/service` 的version与ready；前后端均就绪才算发布完成。即使只改前端，统一版本发布也需要重启后端以加载新版本。
- 日常启动、停止及Agent发布重启统一使用本目录 `scripts/launcher.py`；发布使用 `restart --no-browser`，Windows交给任务计划程序、macOS交给launchd用户服务。禁止直接运行uvicorn、后台Popen或内部serve入口替代正式托管启动；托管失败须报错，不回退为Codex子进程。不设置开机／登录／定时自启，注册信息及本机路径不入Git。首次切换时通过统一入口停止已核验的旧进程，再启动托管服务。
- 具体本机注册、目录迁移和跨平台命令见本目录README的“日常启动”，开发／发布步骤见“开发环境与正式环境”。
