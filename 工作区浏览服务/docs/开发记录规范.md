# 开发记录规范

适用于本服务的开发、修复、排查和维护记录。自2026-10-22起，新记录统一使用[开发记录模板](开发记录模板.md)；历史记录不批量改写，修订时保留原有事实。

## 记录职责

- `docs/开发记录/`：一项工作一份记录，说明为什么改、实际改了什么、怎样验证以及尚未完成什么。
- `docs/版本记录.md`：按真实发布版本概述用户可见的变化，链接到对应W记录。一次发布可关联多份W记录，一份W记录也可以跨多个版本。
- Git：保存代码与文档差异。开发记录不重复粘贴完整diff或工具运行流水。
- 已归档的开发计划表停止维护，不再新增另一张计划表或编号台账。

## 编号与命名

文件保存为 `docs/开发记录/WNNN-事项名称.md`，例如 `W287-取消开发计划入口.md`。编号使用大写W和至少三位十进制数字，不足三位补零；超过999继续使用W1000，不从头编号。正文标题统一为 `# WNNN：事项名称`，事项名称与文件名一致。

1. W编号是开发事项索引，不是发布日期、软件版本号或Git提交号。名称写具体动作和对象，如“取消开发计划入口”，避免“优化”“修复问题”等无法区分的标题。
2. 创建前检查全部现存W记录，包含未提交文件及归档记录，取最大编号加一；不填补空号，不复用已删除或改号的编号。历史改号的旧编号继续保留给原记录。
3. 确定编号后先创建该记录，再开展对应工作。多个会话并行时先核对已落盘的记录；保存前和提交前再次检查编号唯一性。发现冲突时，保留已提交的原编号；多份均未提交时优先调整本次负责的记录，改取当前最大编号加一，并修正它的引用。不覆盖另一会话正在编辑的文件。
4. 同一项工作的补充实现、验证、修正或发布状态更新写回原记录；独立的新需求另建记录。不要为了补一项验证或递增一次软件版本重复建档。
5. 名称以实际交付范围为准。确需改名或纠正重号时，同步修改文件名、正文标题、链接目标和链接显示编号；在本次整理记录中留下旧名与新名对应表，不把所有后续编号整体重排。

## 正文格式

复制模板后删除占位提示，按以下顺序填写。小改动可以很短，不为凑篇幅增加章节。

| 项目 | 填写要求 |
| --- | --- |
| 日期 | 本项工作首次记录日期，格式为YYYY-MM-DD；后续跨日补充增加“更新日期”，不覆盖首次日期。 |
| 状态 | 使用“进行中”“待验证”“待发布”或“已完成”；完成实现不等于完成验证或发布。 |
| 关联版本 | 写实际关联的版本及发布状态，例如“v0.8.17（已发布）”；尚未发布写“未发布”，仅文档整理写“不涉及发布（仅文档整理）”。不得把当前运行版本直接当成本项发布版本。 |
| 修改原因 | 写用户遇到的具体问题、预期结果和本次范围，不抄整段聊天。 |
| 具体改动 | 写最终实现或整理结果。关键文件、取舍和编号迁移有必要才列，避免重复描述未涉及的功能。 |
| 验证结果 | 写实际执行的检查、结果及必要的验证范围。未执行、失败或跳过的检查如实说明，区分模拟检查、真实页面检查和正式发布核对。只列已发生的事实，不预写“通过”。 |
| 未完成事项 | 有待办、失败或需要用户决定的内容才保留此节；写清具体事项。没有则删去整个章节。 |

更新记录时，不能把过去的“未验证”直接改成无依据的“已通过”。完成补验后记录检查结果和更新日期。历史记录缺少日期、版本或验证证据时，不凭编号、文件修改时间或当前运行版本补造。

## 引用与提交

- 引用其他事项时，使用带具体文件路径的Markdown链接，例如 `[W287](开发记录/W287-取消开发计划入口.md)`，路径相对于当前文件；不要仅写“见W287”留下无法定位的文字。
- 提交前核对编号没有重复、文件名与标题一致、模板占位符已替换、修改涉及的相对链接仍可打开。只检查本次变更及其引用影响，不要求每次重写全部历史记录。
- 文档整理不单独递增服务版本或重启服务。涉及代码正式发布时，遵循[服务工作约定](../AGENTS.md)中的版本、构建与发布规则；版本记录写发布摘要，详细过程写W记录。
- 只提交本次工作的修改。按工作区规则创建一次本地提交；不因整理记录自动推送。

历史重号已按首次Git提交先后整理，6组旧名与新名对应关系见[W295](开发记录/W295-统一开发记录规范与重复编号.md)。
